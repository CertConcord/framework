# Upstream sources and draft baseline

Source review date: 5 October 2026. This baseline distinguishes published drafts, editor snapshots and experimental proposals. It does not assign stable status to any of them. Exact URLs, content digests and adapter dependencies are recorded in [source-lock.json](../reference/source-lock.json) and [adapter-lock.json](../reference/adapter-lock.json).

Classification applies to an exact document and edition, not to an organization or protocol family. A mature edition remains an adaptation input while a separately identified successor working draft can be evaluated for concrete improvements. OpenID4VP 1.0 Final and its 1.1 editor draft, for example, have different roles. A successor draft does not authorize a replacement-standard project for the mature edition, and retaining the mature implementation does not justify omitting the successor from research comparisons.

## Established specifications and ecosystems

The adaptation boundary applies to every mature standard and established ecosystem interface, not just particular publishers. The following inventory covers the published specifications in the source registry and the formal standards named by the corresponding application mappings. They remain framework dependencies, not separate replacement-standard projects or targets for new upstream drafts.

An RFC number alone does not mean Internet Standard status. The selected RFC set includes Internet Standards, Proposed Standards and Informational publications. In particular, the published RFC status **Proposed Standard** is distinct from an Internet-Draft. Publication status, implementation coverage and deployment assurance remain separate questions. New normative editions receive compatibility review; they are not relabeled as unpublished research drafts because an adapter is incomplete.

The selected explainer and proposal files match their latest upstream file contents at the review date. An unrelated repository commit does not require changing an otherwise identical source pin. A published W3C edition and a repository's default branch can also represent different development lines; the default branch does not automatically supersede the selected edition.

C2SP publication status is per specification and revision. For example, [signed-note v1.0.0](https://c2sp.org/signed-note@v1.0.0) and [tlog-witness v1.0.0](https://c2sp.org/tlog-witness@v1.0.0) are published stable references even though this composition pins their current editor files. An editor-copy banner does not turn their established protocol semantics into an original CertConcord proposal. Any proposed change must identify the exact unsettled extension and its delta; the C2SP family as a whole is not a draft-extraction candidate.

## Compatibility findings

The implemented OpenID adapters continue to select the named 1.0 Final profiles. Their response encryption uses ECDH-ES JWE, and issuance uses the declared authorization-code and pre-authorized flows. The ISO Annex C HPKE adapter is a different protocol and does not establish JOSE HPKE support. The current runtime does not implement the 1.1 Authorization Challenge Endpoint or its `auth_session` state machine and does not advertise 1.1 conformance. Adoption requires explicit algorithm negotiation, context/substitution tests and lifecycle/replay tests for the newly selected behavior. A source pin alone cannot enable that behavior.

The current C2SP cosignature editor text changes presentation-language references and structure names relative to `v1.1.0-rc.1`. Its selected signature inputs, algorithm type bytes and subtree domain remain unchanged. Its MTC revision-07 citation does not establish revision-07 compatibility: the published MTC baseline is revision 06. CertConcord's MTC/C2SP/governance composition retains its own policy requirements and claim boundaries in [adapters](adapters.md).

The MTC editor already fixes the landmark row limit in [upstream PR 337](https://github.com/ietf-plants-wg/merkle-tree-certs/pull/337). The existing `latestNumber + 1` rule therefore aligns with an upstream correction and is not an unresolved contribution candidate. Other editor changes include the PKIX OIDs `1.3.6.1.5.5.7.6.67`, `1.3.6.1.5.5.7.25.3` and `1.3.6.1.5.5.7.1.38`, GREASE cosignatures including landmark-relative certificates, extensibility registries, and renamed cosignature/proof structures. Those changes are part of the current research comparison; the existing adapter still identifies and verifies draft-06 certificate bytes. Adopting the editor's certificate profile requires explicit identifier and verifier dispatch, corresponding negative vectors, and historical interpretation under the [evolution rules](evolution.md). The editor snapshot must not be described as published draft-07 support.

ARKG revision 11's three P-256 vector sets match the committed contexts, derivation inputs, public keys and tickets. Split-signing revision 01 separates the signing-operation algorithm from the verification algorithm: for the selected P-256 split operation, the caller hashes once and the signer performs the remaining ECDSA steps. Preview value `-300` is not an assigned IANA value for ESP256-split. The selected ARKG operation, seed and argument values are likewise experimental identifiers. These values are meaningful only within the explicitly selected [Passkey signing profile](../spec/bindings/PSCP-draft-02.md).

## Adaptation and contribution boundaries

All established specifications and ecosystem interfaces above remain adaptation and reference inputs within the integrated framework. The same treatment applies to further mature dependencies. Original CertConcord capabilities may draw on their designs while stating their own application problem, semantics and compatibility limits. Using an existing extension point for a new application profile does not constitute a proposal to replace the underlying standard.

Work on an upstream draft starts with a specific limitation in its current text or implementation. A correction belongs with that draft when its existing contract can express the solution. An independent proposal needs a separable contract, a reason existing mechanisms cannot express it, and reproducible positive and negative evidence. A source citation, module or acronym alone is not a repository boundary. [Research development](research.md) defines proposal content; [MTC document validation](mtc-document-validation.md) supplies the current application focus.
