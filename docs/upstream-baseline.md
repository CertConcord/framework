# Upstream sources and draft baseline

Source review date: 20 October 2026 for published standards, working drafts and the semantic deltas below; the deployment-use-cases WG successor was separately reviewed on 25 October 2026. Exact selected URLs and content digests remain in [source-lock.json](../reference/source-lock.json) and [adapter-lock.json](../reference/adapter-lock.json). A retained source pin identifies the evaluated bytes; it need not be the newest available text. Vendor implementation snapshots retain their earlier selections unless a concrete delta is identified.

Classification applies to an exact document and edition, not to an organization or protocol family. A mature edition remains an adaptation input while a separately identified successor working draft can be evaluated for concrete improvements. OpenID4VP 1.0 Final and its 1.1 editor draft, for example, have different roles. A successor draft does not authorize a replacement-standard project for the mature edition, and retaining the mature implementation does not justify omitting the successor from research comparisons.

## Compatibility findings

The implemented OpenID adapters continue to select the named 1.0 Final profiles. Their response encryption uses ECDH-ES JWE, and issuance uses the declared authorization-code and pre-authorized flows. The ISO Annex C HPKE adapter is a different protocol and does not establish JOSE HPKE support. The current runtime does not implement the 1.1 Authorization Challenge Endpoint or its `auth_session` state machine and does not advertise 1.1 conformance. Adoption requires explicit algorithm negotiation, context/substitution tests and lifecycle/replay tests for the newly selected behavior. A source pin alone cannot enable that behavior.

The selected C2SP cosignature text changes presentation-language references and structure names relative to `v1.1.0-rc.1`. Its signature inputs, algorithm type bytes and subtree domain are unchanged in the v1.1.0 release. CertConcord's separate ML-DSA-87 identifier and MTC/C2SP/governance composition retain their own policy requirements and claim boundaries in [adapters](adapters.md).

MTC revision 07 assigns the PKIX OIDs `1.3.6.1.5.5.7.6.67`, `1.3.6.1.5.5.7.25.3` and `1.3.6.1.5.5.7.1.38`, registers extensible parameters, permits GREASE cosignatures and uses versioned C2SP references. The selected verifier applies these identifiers, preserves unknown entry-extension bytes in the Merkle leaf, ignores unknown cosigners for quorum, and rejects malformed ordering and unknown critical X.509 extensions. It rejects old and mixed identifiers rather than rewriting retained evidence. [Evolution](evolution.md#mtc-revision-07-selection) states the cutover and original-verifier boundary. The landmark row-bound correction in [upstream PR 337](https://github.com/ietf-plants-wg/merkle-tree-certs/pull/337) is incorporated in the published revision.

ARKG revision 11's three P-256 vector sets match the committed contexts, derivation inputs, public keys and tickets. Split-signing revision 01 separates the signing-operation algorithm from the verification algorithm: for the selected P-256 split operation, the caller hashes once and the signer performs the remaining ECDSA steps. Preview value `-300` is not an assigned IANA value for ESP256-split. The selected ARKG operation, seed and argument values are likewise experimental identifiers. These values are meaningful only within the explicitly selected [Passkey signing profile](../spec/bindings/PSCP-draft-03.md).

## Adaptation and contribution boundaries

All established specifications and ecosystem interfaces above remain adaptation and reference inputs within the integrated framework. The same treatment applies to further mature dependencies. Original CertConcord capabilities may draw on their designs while stating their own application problem, semantics and compatibility limits. Using an existing extension point for a new application profile does not constitute a proposal to replace the underlying standard.

Work on an upstream draft starts with a specific limitation in its current text or implementation. A correction belongs with that draft when its existing contract can express the solution. An independent proposal needs a separable contract, a reason existing mechanisms cannot express it, and reproducible positive and negative evidence. A source citation, module or acronym alone is not a repository boundary. [Research development](research.md) defines proposal content; [MTC document validation](mtc-document-validation.md) supplies the current application focus.

## Remote signing recovery boundary

[CSC API 2.2.0.0](https://cloudsignatureconsortium.org/wp-content/uploads/2025/11/csc-api.pdf), sections 11.13-11.15, already defines asynchronous signing: an asynchronous `signHash` or `signDoc` response supplies a server-generated `responseID`, and `signatures/signPolling` queries the outcome using that value as `requestID`. Section 7.5 permits arbitrary optional `clientData`, such as a transaction identifier, but says the remote service MAY use or log it. These clauses do not assign `clientData` an idempotent execution or recovery meaning. Polling covers a known `responseID`; it does not by itself recover a result when the initial signing response, including that identifier, was lost. The synchronous profile in [CSC selection](csc.md) does not implement the asynchronous methods and keeps interrupted execution unresolved.

[ETSI TS 119 432 V1.3.1](https://www.etsi.org/deliver/etsi_ts/119400_119499/119432/01.03.01_60/ts_119432v010301p.pdf), clauses 7.5-7.7, references those CSC signing and polling methods and permits a synchronous-only selection. It must not be described as lacking all asynchronous result retrieval. The separate [EN 319 432 work item](https://portal.etsi.org/webapp/WorkProgram/Report_WorkItem.asp?SearchPage=TRUE&WKI_ID=75464) lists stable draft 1.3.4 dated 12 October 2026; its authenticated draft text has not been evaluated here, and its publication status is not that of the published TS. A narrower interoperability question is whether a provider can durably bind a client-supplied operation identifier to exact signing input and return the original outcome after a lost initial response, without another key invocation. That behavior requires explicit provider support; an application cannot infer it from `clientData`, a timeout or a local journal. The [signing-context component](../spec/external/signing-context/draft.md) retains the failure cases without requiring framework-specific permit and receipt objects in another protocol.

## Selected mdoc base and public WG10 development text

The independent mdoc component selects ISO/IEC 18013-5:2021 edition 1 as the published background. The [ISO catalog](https://www.iso.org/standard/69084.html) was checked on 20 October 2026 and separately identifies a DIS successor under development. The full licensed 2021 text was not reviewed; catalog metadata and Multipaz cross-checks cannot establish full ISO conformance.

[ISO/IEC TS 23220-4:2026](https://committee.iso.org/standard/86785.html?browse=ics) is a published source of general mdoc operational-phase building blocks and explicitly allows document-specific profiles. Its public abstract excludes how consent to share is obtained and requirements on mdoc data or private-key storage; it does not itself certify an application document-signing key or document-signing intent. [ISO/IEC DIS 23220-7](https://www.iso.org/standard/90046.html?browse=tc) is still under development and proposes registration procedures for mdoc types and namespaces. Neither source grants registration or ISO conformance to `org.certconcord.signer.1`. The independent [mdoc signing profile](../spec/external/mdoc-signing/draft.md) therefore remains an experimental application contract with its own issuer admission, purpose and detached-signature checks, not an amendment to ordinary mDL presentation.

The separately pinned `wg10WorkingDraft` is the public September 14, 2025 CD-ballot-resolution PDF from [WG10 commit b250e7a6](https://github.com/ISOWG10/ISO-18013/tree/b250e7a64f99e22ceed10d2a5799bed38ee89f85), blob `70af94f67df47e6d35ac5b055201892688c1c11a`. Its cover identifies it as preceding a DIS ballot; it is not the published standard or proof of the latest DIS text. The reviewed sections 12.3.4 and 12.3.6 address protected certificate thumbprints and optional MSO revocation. The source hash is retained without redistributing the PDF.

The component uses existing RFC 9360 protected `x5t` for issuer-certificate binding. It selects one application namespace status-list reference with JWT evidence and externally admitted status evaluation against Token Status List draft 21. The public WG10 text instead places revocation in MSO status and uses COSE/CWT lists while citing draft 12. This difference is explicit: no second runtime or implicit fallback is introduced, and no second-edition conformance is claimed. Qualification, issuer/RA admission, PQ seals, transparency, operations and historical evidence closure remain framework policy.
