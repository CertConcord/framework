# ACME Directory profile metadata

The selected ACME Profiles contract uses `Directory.meta.profiles`, as specified by [draft-ietf-acme-profiles-02 sections 3 and 4](https://www.ietf.org/archive/id/draft-ietf-acme-profiles-02.txt). The surrounding `meta` object is the service metadata extension point defined by [RFC 8555 section 7.1.1](https://www.rfc-editor.org/rfc/rfc8555.html#section-7.1.1).

The reference service advertises its configured profile names and description URLs inside `meta.profiles`. Optional `termsOfService` shares the same metadata object. An empty configured profile list produces an empty map. The directory's five operation endpoints retain their existing values.

For an explicit `newOrder` selection, the reference client requires a primitive string, a non-null metadata object and profile map, and an own map entry whose selected value is a nonempty string. Arrays do not satisfy either object contract. Names are compared exactly, including case; an explicitly advertised special property name remains ordinary data. Validation concerns the selected entry, so an unrelated extension or unselected value does not change an otherwise valid selection. Description values remain opaque metadata; external and `data:` descriptions are supported without fetching them or requiring the operation endpoint's origin.

The nonstandard top-level `Directory.profiles` field is not a fallback. A legacy-only advertisement cannot admit an explicit selection, and a valid top-level entry cannot repair missing or malformed `meta.profiles`. When both locations occur, only the standard metadata entry contributes. Callers that omit `profile` retain the existing default-selection flow; this does not require a profile map. The authenticated service still selects its configured default and enforces its own allowed profiles and issuance policy.

An unadvertised or malformed explicit selection raises `ACME_PROFILE` before a nonce request or order POST. Duplicate JSON members are rejected by the directory parser. Discovery does not authorize enrollment: nonce consumption, ES256 JWS verification, account status and ownership, challenge validation, CSR binding, RA approval and issuance checks retain their separate gates. DNS control and a profile advertisement do not establish natural-person identity or document-signing authority.

[acme-profile-metadata.json](../reference/vectors/acme-profile-metadata.json) freezes synthetic metadata JSON fragments and their SHA-256 values, including duplicate-member inputs. [acme-profile-metadata.test.mjs](../reference/acme-profile-metadata.test.mjs) inserts those exact bytes into an independently constructed loopback Directory envelope. Its HTTP fixture checks the actual client request with Node's ES256 verification primitive, including protected URL, account identifier, nonce and exact payload. Signature, payload, key and nonce substitutions test that oracle. Service advertisements are checked separately against the standard shape, with and without terms, rather than using the service's output as the client's only fixture.

The existing [ACME account tests](../reference/acme.test.mjs), [enrollment exchange](../reference/enrollment-network.test.mjs), [enrollment security tests](../reference/enrollment-security.test.mjs) and [managed-device enrollment](../reference/device-enrollment.test.mjs) cover the adjacent admission boundaries. These synthetic fixtures establish the selected directory contract and bounded regressions; a complete independently developed ACME implementation and operational CA qualification remain separate evidence.
