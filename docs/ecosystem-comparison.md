# Composition benchmarks for document trust

CertConcord's first complete target remains a purpose-bound document certificate lifecycle, from qualification and issuance through authorized operation, retained status, offline verification and timely preservation renewal. Comparative implementations are a way to test this contract, not a replacement for an independently implementable specification or a requirement to operate every infrastructure component. This comparison records capabilities of the cited systems, not a claim that any combination is unable to satisfy a CertConcord requirement.

Feature checklists are insufficient evidence of equivalence. A comparison must identify the exact claim, signed bytes, externally admitted authority, key and purpose, state time, knowledge time, freshness, recovery behavior and non-accepting result when evidence is missing or contradictory. A source link or a successful primitive check does not establish application-level interoperability.

## Established systems and implementation references

The SCITT RFCs and the explicitly named individual Internet-Draft are pinned in the [source registry](../reference/source-lock.json). The other official project links are living comparison references, not selected protocol editions or assertions of current implementation compatibility. Their capabilities must be checked against an exact release before a deployment or interoperability claim.

## Reduction and interoperability tests

For every additional signed object, status transition or verifier, record the exact threat and a counterexample using existing fields or extension points. Preserve a separate object only when distinct authorities or ordering create a claim that an existing object cannot carry without changing its meaning. In the selected offline attested plan, a permit precedes dispatch and a receipt follows execution. A separately encoded SCITT Signed Statement could report either event, but its registration receipt cannot collapse those two trust decisions. The [composition review](composition-review.md) records the current object-by-object decisions.

The highest-value experiments compare bounded claims rather than forcing unrelated systems through one universal feature matrix:

1. Replay the same original CMS/PDF bytes, status, timestamp and renewal boundaries against a selected DSS version and the CertConcord adapter. Record differences in signed revision coverage, historical authority, policy and result classification; do not infer an ETSI level from detached ERS alone.
2. Cross-consume a selected native signer-mdoc's original issuer and document bytes with an independently implemented ISO/COSE stack. Test exact key, purpose, issuer and status separation; an ordinary mDL presentation is a negative control, not a document signature.
3. Measure a tile-log personality against the selected MTC/C2SP bytes and failure cases before replacing reference storage. A published checkpoint, a witness consistency claim and a mirror's durable possession remain separate observations.
4. Compare a Sigstore bundle or SCITT transparent statement with the corresponding CertConcord claim at an explicit state and knowledge time. Record missing later status, authority and preservation evidence as missing rather than translating a valid inclusion proof into document trust.

These experiments can reuse mature parsers and providers. They do not substitute for a second independently developed implementation of the complete mandatory document profile, an external security assessment or deployed operational assurance. The [conformance record](../spec/conformance.md) controls those claims.
