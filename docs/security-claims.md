# Security claims by evidence path

The framework's trust decision combines multiple assertions. The algorithm on one assertion cannot strengthen a different assertion. The following matrix describes reference paths and their limits; it is not an independent security assessment.

The MTC/C2SP/RRA combination is CertConcord's composition. IETF MTC defines the selected certificate/proof and cosigner semantics; C2SP defines separately selected transparency protocols. CertConcord supplies the governance, membership/quorum policy and document-operation bindings. The ML-DSA-87 C2SP identifier is a CertConcord extension. These layers have separate assumptions and review obligations.

| Assertion or operation                 | Selected protection                                                                                                  | What verification establishes                                                                              | Remaining assumption                                                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| External mDL/photoID identity evidence | Issuer/holder algorithms selected by the identity profile, commonly classical EC                                     | Accepted issuer, disclosed claims, holder/session proof and the configured status checks                   | Truth of identity claims, issuer governance, wallet custody and external ecosystem rules                                |
| Native mdoc issuer authentication      | Selected ISO-compatible issuer signature; separate PQ credential seal and witnessed issuance evidence where selected | Exact native credential, operation key, purpose and accountable issuance under configured authorities      | The PQ seal does not transform a classical DeviceKey proof into PQ authentication                                       |
| MTC certificate admission              | Merkle inclusion with SHA-256 and configured CA/mirror signature suites, ML-DSA-87 in the document example           | Membership in the accepted issuance interval and signatures from the required configured operators         | Actual operator independence, non-equivocation monitoring, historical availability and privacy                          |
| Registration authorization             | ML-DSA CMS in the examples; certificate commits to the signed RA authorization body                                  | RA-approved subject, public key, purpose, policy and issuance request                                      | RA identity decision, possession-certificate acceptance and custody assessment                                          |
| Ordinary Passkey activation            | WebAuthn challenge bound to exact activation; classical authentication where selected                                | RP/origin, authenticator assertion, permitted user verification and operation binding                      | Display integrity, device capability, authenticator compromise and authority behavior                                   |
| Proposed Passkey document signature    | Selected raw-signing proposal with admitted key; ES256 in current Passkey document-key profiles                      | The exact document signature and its admitted key/policy binding                                           | Proposed extension availability, device enforcement and classical signing security                                      |
| Independent PQ document key            | ML-DSA-65 or ML-DSA-87; CMS/COSE profile binding                                                                     | Signature integrity and exact covered bytes under the certified document key                               | Admission path, activation method, provider access and custody remain separate                                          |
| Organizational seal authorization      | Authority-signed operation grant, permit commitment and status                                                       | A configured institutional authority attested a particular actor and operation                             | Organizational entitlement checking is attested; no hierarchical or legal qualification inference                       |
| Document encryption                    | ML-KEM-768/1024, HKDF-SHA256, AES-256-KW and AES-256-GCM                                                             | Confidentiality/integrity under the selected KEM and symmetric assumptions, with recipient/context binding | No sender authentication or forward secrecy against later recipient-key compromise; all recipients can read the content |
| Trusted proof of existence             | RFC 3161 token from an explicitly accepted TSA; ML-DSA or externally selected TSA signature                          | Committed bytes existed by the conservative upper bound, subject to TSA trust/status                       | Clock accuracy, TSA operations and algorithm security; no exact signing-time or consent proof                           |
| Encryption-key recovery                | Two distinct authority approvals, bound KEM envelope and authenticated vault                                         | The configured threshold authorized release to the specified replacement key                               | Escrow custody, operator independence and local import/erasure; no restoration of signing authority                     |
| Archive continuity                     | Explicitly selected evidence-record renewal and original-byte retention                                              | Integrity of a supported evidence chain and accepted renewal proofs                                        | Timely renewal, retained trust/status material and reviewed algorithm transitions                                       |

For the document example, document signatures, RA controls, MTC signatures, organizational authorization and TSA signatures use ML-DSA; recipient encapsulation uses ML-KEM. Every private key is software-generated and the clock/status services are synthetic. That example therefore demonstrates protocol composition, not production PQ assurance or hardware protection.

For a native mdoc or Passkey path, the document signature can remain verifiable under a PQ key while a classical identity or activation component is still relevant to the authenticity of the admitted signer. Reports must distinguish retrospective signature integrity from resistance to identity/authorization forgery at operation time. A single blanket “post-quantum workflow” label loses this distinction.

Cryptographic transitions need a new explicit suite or binding, authenticated policy selection, exact old-byte retention and a stated historical-verifier policy. A verifier must not retry a weaker suite after a verification failure. Original suite designs and MTC alternatives require separate analysis and interoperability evidence before promotion.

The [document binding](../spec/bindings/DOCUMENT-draft-03.md) specifies the current composition. [Conformance](../spec/conformance.md) records the remaining independent-implementation, platform and operational gaps.
