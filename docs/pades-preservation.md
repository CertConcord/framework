# Selected PAdES preservation profile

This adapter implements a bounded PDF preservation path under the published [ETSI EN 319 142-1 V1.2.1 (2024-01)](https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf). Its requested levels are PAdES-B-B, B-T, B-LT and B-LTA, represented as `B`, `T`, `LT` and `LTA`. A level requires verified dependencies under the caller's external policy. Finding a DSS dictionary or a timestamp field alone does not establish a level.

The selected document profile is unencrypted PDF 1.7 with classic cross-reference tables, one approval signature and incremental DSS/document-timestamp revisions. Document, certificate, CRL and timestamp signatures use P-256/SHA-256. Timestamp imprints may use SHA-256 or SHA-512. Certificate paths contain a leaf and an externally admitted self-signed root; status uses full direct CRLs. This is a finite-horizon classical profile. It does not claim post-quantum or qualified-signature status.

Import the APIs directly from `reference/pades.mjs`. The packaged ECP verifier and existing `pdf.mjs` adapter retain their separate acceptance contracts. The shared `ades-cms.mjs` primitives have explicit `CADES`, `PADES` and `RFC3161` profiles; reusing them does not apply the CAdES signing-time attribute requirement to PDF signatures.

## Creation and augmentation

`await preparePAdESSignature(pdf, {certificate, certificates, signingTime, signatureBytes?, fieldName?, algorithmProfile?})` returns `tbs`, `byteRange`, `contentHash` and an asynchronous `finish(signature)`. The content hash is SHA-256 over the exact ByteRange content. The signature is detached DER CMS with `id-data`, content type, message digest and SigningCertificateV2. Both signer and root certificates are embedded in this selected B profile. The standard mandates the signer and recommends other available path certificates; requiring the direct root here is an explicit stricter selection.

The PDF signature dictionary has `/Type /Sig`, `/SubFilter /ETSI.CAdES.detached` and a mandatory `/M` PDF date. Generation writes a UTC date including seconds. Verification also accepts complete numeric UTC offsets. The published baseline forbids the CMS signing-time attribute and the approval dictionary's `/Cert` entry. Exactly one SignerInfo is mandatory within each PDF CMS container; more than one is invalid. Additional PDF approval signatures are a separate, unselected capability. The PDF date is a self-claimed time, never proof of existence. Missing `/M` is indeterminate; a malformed date is invalid, including impossible supplied fields in a partial date. Valid dates with incomplete precision, unspecified timezone or a time before the selected nonnegative Unix-time range are unsupported.

`finish(signature)` verifies the supplied CMS mathematics, certificate binding and structural profile before returning the completed PDF. It receives no trust policy and grants no B-level acceptance verdict. Call `verifyPAdES` with explicit external policy and times for that decision. All public buffers, input parameters and callback-facing decisions are copied at the asynchronous boundaries.

`await preparePAdESAugmentation(pdf, {targetLevel, validationMaterial, timestampRequestOptions, policy, signatureBytes?, fieldName?})` prepares a byte-preserving update. `validationMaterial` contains DER `certificates` and `crls`. `LT` appends DSS material without requesting a timestamp. `T` and `LTA` append a document timestamp, returning its `requestDER`, `imprint` and `hashOID`. Obtain the RFC 3161 token externally, then call `await finish(token, {validationTime, knowledgeTime, policy?})`. For LT, pass no token. Finish verifies the requested level using the supplied evaluation times and a snapshotted or explicitly replaced complete policy.

The API performs no network operation, durable publication or scheduling. A service composing it with a TSA and durable storage must retain the exact prepared bytes, request and uncertain response state. A lost response does not show that the earlier TSA operation failed.

## Levels and exact revision coverage

| Level | Required validated dependencies                                                                                                                                   |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B     | Exact detached content and signature, required fields, ESS binding, embedded selected certificate path, external authority and status policy                      |
| T     | B plus a trusted document timestamp establishing approval-signature existence by the selected validation time                                                     |
| LT    | T plus embedded validation material for the approval and all existing timestamp signers                                                                           |
| LTA   | LT plus a trusted document timestamp covering the DSS and preexisting signature/timestamp dependencies, with continuous protection through current knowledge time |

The initial implementation selects the document-timestamp route to T. The published standard also permits a CMS signature timestamp; that route remains unsupported here. A CAdES archive-timestamp attribute is not a substitute for the PDF preservation route. CAdES-defined attributes absent from the published PAdES Table 1, including CMS signing-time and CMS algorithm protection, are rejected according to that baseline. Standard-permitted optional features outside this selection are reported as unsupported.

A document timestamp uses `/Type /DocTimeStamp` and `/SubFilter /ETSI.RFC3161`. An optional `/V` must be zero. The six fields forbidden by EN 319 142-1 clause 5.4.3 are rejected. Its separate recommendation to omit `Name`, `M`, `Location`, `Reason` and `ContactInfo` is not treated as a mandatory prohibition; these descriptive fields do not establish trusted time.

Every ByteRange covers its complete signed revision except the exact source span of its own Contents hexadecimal string, including the angle delimiters. The excluded bytes must contain one strict DER value followed only by zero padding. Matching another dictionary's equal Contents value is insufficient. Cross-reference entries, object numbers/generations, Prev links, revision boundaries and field-to-signature associations are checked. Duplicate dictionary keys are rejected after decoding PDF name escapes.

The DSS uses standard `Certs` and `CRLs` arrays of indirect DER streams. Every stream must match its declared certificate or CertificateList schema, including unused material. A well-formed unused certificate does not become a trust anchor. Uncompressed and bounded Flate streams are selected. Each parsed revision retains only the cumulative material actually present then. Later DSS additions never acquire historical proof from an earlier timestamp. A timestamp covering an earlier approval and its DSS can authenticate those exact material bytes; it cannot authenticate its own otherwise unprotected TSU material.

After approval, only selected preservation changes are permitted: document timestamp fields, their minimal form/catalog references and cumulative DSS objects. Earlier signatures and signed content must remain present. Page content, visible annotations and unrelated objects cannot be altered by appending a valid timestamp. New output declares the published ADBE PDF 1.7 ExtensionLevel 8 alternative.

`originalPDF`, when supplied to verification, checks an exact original byte prefix and approval continuity. It does not import identity qualification, consent or an organizational authorization decision. Retain original ECP evidence separately; appending to the PDF changes its complete-object hash and cannot replace an existing ECP leaf while retaining that leaf's old digest.

## Authority, status and time

`verifyPAdES(pdf, {minimumLevel, originalPDF?, validationTime, knowledgeTime, policy})` uses the same selected authority and material contract as the [CAdES adapter](cades-preservation.md#authority-status-and-time). The caller supplies exact `trustedRoots`, scoped `authorityResolver`, accepted `timestampPolicies` and finite exclusive `algorithmDeadlines`, `hashDeadlines` and `keyDeadlines`. `currentMaterial` can supply current authentication and later-known status; it does not supply embedded LT closure or historical PDF coverage.

`validationTime` may be historical. The initial trusted proof must establish signature existence by that time. Later preservation proofs may follow it, provided they are known by actual `knowledgeTime` and protect the relevant prior bytes before their cutoffs. All authority and incident queries use that actual knowledge time. An old claimed PDF date, CRL thisUpdate or timestamp genTime cannot authenticate a newly encountered object after its cryptographic protection has been lost.

The newest unprotected timestamp must remain authentic at knowledge time. Earlier timestamps may rely on later authenticated coverage of their exact bytes and validation material. Ordinary certificate expiry is distinct from the cryptographic deadline of an already preserved signature. Equality with a protection cutoff fails, and a late renewal cannot repair a lost interval. The full RFC 3161 accuracy interval is evaluated; absent accuracy is indeterminate, never silently zero.

## Results and limits

The result contains an overall status, reason, requested level, any established lower level, modification decision and proof diagnostics. Established malformed encoding, invalid mathematics, bad bindings, forbidden changes and authenticated applicable revocation are `INVALID`. Recognized unselected features are `UNSUPPORTED`. Missing mandatory evidence, unavailable policy, stale status and unresolved knowledge are `INDETERMINATE`. Available established invalidity takes precedence over unsupported capability, which takes precedence over uncertainty. Every non-VALID result prevents acceptance.

The selected parser excludes linearized PDFs, encryption, object/xref streams, hybrid xref, indirect stream lengths, XFA, active/external content, certification/FieldMDP transforms, additional approval signers and unknown extension semantics. OCSP, VRI and general certificate-path construction remain outside this implementation. A structurally safe unsupported input retains extractable signatures for mathematical failure detection; a fatal structural parse failure cannot provide that guarantee. No recovery parser or weaker fallback is used for acceptance.

Untrusted PDF parsing runs in a bounded worker that receives no keys or policy callbacks and performs no network operation. Explicit limits include 64 MiB input, 20,000 object slots, 32 revisions/signatures, 128 objects per DSS material array and 16 MiB decoded DSS material. Resource exhaustion is a non-accepting result. These bounds and use of the pinned pdf-lib object parser do not establish production parser or rendering assurance.

The selected source is the published 2024 edition. EN 319 142-1 V1.3.0 (2026-08) was an approval draft when reviewed on 2026-10-07; its changed PDF/CMS requirements are not silently selected. PDF byte and revision rules were checked against the [Adobe-authorized ISO 32000-1:2008 text](https://raw.githubusercontent.com/adobe/dc-acrobat-sdk-docs/b21b8bca628d7e436b5d19e00ae161c0f5e52e4a/docs/standards/pdfstandards/pdf/PDF32000_2008.pdf). Exact source digests are retained in `source-lock.json`.

Independent pyHanko 0.37.0 testing reports parsing, digest/signature, path/status and modification checks separately. Its complete AdES LTA procedure imposes an additional CMS signature-timestamp constraint even when a document timestamp provides T under the selected published ETSI route. This tool boundary must be reported; primitive/path successes alone are not complete independent PAdES preservation conformance. The repository remains a working draft subject to [independent implementation and external assessment gates](../spec/conformance.md).
