# Composition and reduction analysis

CertConcord's additional semantics are application policy, authority separation and evidence requirements. They do not establish that existing standards are incapable of representing these requirements. A new name, hash domain or signed wrapper is not an independently proven security primitive. Each extra verifier, key, freshness rule and durable state increases the composition's attack surface.

This analysis covers the shared reference state, enrollment, activation, evidence, recovery and selected document paths. It is source analysis with synthetic adversarial tests, not an independent cryptographic assessment or a proof of every adapter. All profiles remain working drafts.

## Standard representations and additional semantics

CMS SignedData and attributes provide signed containers; COSE supplies protected headers and signature structures. Neither format determines who may authorize a CertConcord document operation. The remaining work is to specify those semantics without unnecessarily introducing another signed object. [RFC 5652](https://www.rfc-editor.org/rfc/rfc5652.html), [RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html).

| Mechanism and code | Existing representation | Additional requirement in this composition | Reduction decision and remaining obligation |
| --- | --- | --- | --- |
| Subject/key qualification: `enrollment.mjs`, `identity.mjs` | PKCS #10, CMP/ACME enrollment, issuer certificate fields; CMS can carry an RA decision | A CA consumes one scoped RA decision for an exact subject, key, purpose and policy; accepting a government identity issuer grants no signing-issuer authority | Retain RegistrationAuthorization in the current independent RA/CA path. A CSR proves key use, not identity qualification. A successor using an already authenticated enrollment exchange could avoid a separate RA envelope, but must preserve independently verifiable issuer qualification commitments and retry semantics. No claim that CMS itself needs replacement. |
| Document intent: `pki.mjs`, `signer-mdoc.mjs`, `evidence.mjs` | CMS signed attributes, COSE protected headers and format-specific signed properties | Bind document scope, certified key, purpose, policy and transaction to the actual container input | SIM is unsigned data committed by the document signature. No separate SIM signature is needed. Policy and intent commitments should stay in the selected container's existing extension points. Extra standalone intent certificates are unnecessary. |
| Activation and qualification: `webauthn.mjs`, `bridge.mjs`, `state.mjs` | WebAuthn challenge and assertion; OpenID4VP transaction data and holder transcripts | Bind an approved operation to the original session, RP, audience, exact key/input and one-use nonce | Retain the application context as challenge data. Qualification-to-operation binding is a validation rule, not another signature format. ActivationContext is also copied into the evidence package although the permit already carries it; this is a removable duplicate in a successor evidence plan, not grounds to accept conflicting copies today. |
| OperationPermit and ExecutionReceipt: `state.mjs` | CMS controls; a selected CSC deployment also has its authorization/SAD protocol | Preserve a pre-dispatch authorization and a later provider result under independently configured authorities | Retain both controls in the current offline attested plan. A post-execution receipt cannot supply prior consent, and a permit cannot prove a result. Their necessity depends on this trust split. A future co-located-authority or CSC-only profile needs an explicit evidence model before either control can be removed. CSC SAD is not assumed to be portable offline evidence. |
| Local capability enrollment: `lifecycle.mjs` | Authenticated WebAuthn enrollment plus a current database record | Bind a local capability public key to the registered credential, subject and document key | Return unsigned public metadata. Remove the CapabilityRegistration CMS output and the registry's signing-key dependency: no independent verifier consumes that envelope, and `active()` reads the authenticated journal. Replay and signed revocation checks remain. This interface grants no portable capability. |
| Trust manifests: `state.mjs` | Signed, versioned policy metadata and externally provisioned trust anchors | A monotonic LIVE watermark, separate historical reads, and explicit root authority | Retain fixed-pin manifest verification. Remove the in-memory `rotate()` operation and per-call root/threshold overrides. Root rotation is unsupported until pin set, threshold and continuity state can be authenticated and persisted atomically. Historical reads must not reset LIVE state. |
| PRF wrappers: `protection.mjs` | WebAuthn PRF, HKDF, AES-GCM or key wrap | Purpose/epoch separation and preservation of the same root during rewrap | Combine verification and commit in one transaction. No durable NEW_WRAPPER_VERIFIED state or separate `verify()` call is needed. The wrapper bytes and derivations are unchanged. Local vault chunking and extra KW metadata authentication remain custom compositions requiring assessment; PRF protection is optional to ordinary WebAuthn signing. |
| Evidence package: `state.mjs`, `evidence.mjs`, `signer-mdoc.mjs` | Existing container evidence properties, RFC 3161 tokens and RFC 4998 evidence records | A selected complete verification plan across qualification, operation and lifecycle evidence | The package adds no mandatory signature on its manifest. Its graph is not an authority source. Current document plans use one plan with leaf objects; generic nested graphs add no demonstrated benefit for those plans. Flattening that envelope and removing duplicated activation/context fields remain candidates for a new wire revision. Existing plan hashes and timestamp imprints cannot silently change. |
| Organizational authorization: `document-evidence.mjs` | CMS signed authorization plus authenticated lifecycle status | An independent institution authorizes one actor, key and operation | Retain the grant when the organization and activation attestor are distinct authorities. A permit commits to the grant; it does not replace institutional authority. Hierarchical delegation is not implemented. A co-located authority profile might combine the grant and permit, with explicit scope and revocation semantics. |
| Native signer mdoc: `signer-mdoc.mjs`, `credential-log.mjs` | ISO issuerAuth/MSO and COSE document signatures | Certify a document key/purpose and add separately declared PQ certification and issuance evidence | The PQ seal adds a signed object because the selected ISO issuer path is classical. It is a deliberate CertConcord composition cost, not an ISO requirement or a PQ upgrade to the holder proof. Removal needs an interoperable issuer-authentication path that actually provides the selected certification property. |
| Certified encryption: `document-encryption.mjs`, `protection.mjs` | CMS AuthEnvelopedData/KEMRecipientInfo and the selected algorithms | Admit the recipient's certified KEM key and verify possession before delivery | Preserve the standard envelope. RFC 9883 signed possession statements and the direct KEM challenge establish different claims; requiring both is a selected admission policy. The custom challenge and context binding need independent analysis or replacement by an applicable standardized enrollment proof. Encryption does not authenticate a sender or establish signing intent. |
| Optional Passkey/execution proposals: `passkey-credentials.mjs`, `execution-binding.mjs` | Pinned raw-signing/ARKG proposals and existing provider APIs | Certify a distinct signing key or attest a governed broker's enforcement boundary | Keep outside the mandatory document baseline. EBP adds a signed provider admission and durable key lock; its claim cannot be inferred from a generic raw-signing API. These experiments do not justify adding equivalent layers to ordinary WebAuthn activation. |

Recovery reachability is a local model of administrator, escrow and provider capabilities. It is neither a signed object nor a proof that the model includes every deployment path. Empty or unknown signing targets are rejected; otherwise a misspelled target could incorrectly pass the separation check. Encryption recovery still requires independent approvals and an authenticated result because it releases key material across an authority boundary. Those signatures are not duplicates of the local graph calculation.

## MTC, transparency and governance provenance

| Source | Selected responsibility | CertConcord addition |
| --- | --- | --- |
| [IETF MTC draft-06](https://datatracker.ietf.org/doc/html/draft-ietf-plants-merkle-tree-certs-06) | Certificate/proof syntax, issuance logs, subtree/cosigner semantics, standalone and landmark-relative verification | RRA qualification, operator admission, selected quorum policy, document intent and preservation obligations |
| Separately pinned C2SP mirror/witness protocols | Checkpoint transport, mirroring/witness interfaces and their distinct statements | Governed membership, failure assumptions and an explicitly named ML-DSA-87 extension |
| CertConcord RRA binding | Domain authority, policies and application evidence requirements | The composition itself; it requires its own analysis and independent implementation |

MTC defines cosigner semantics; CertConcord selects which operators and statements its policy trusts. A consistency witness does not establish durable possession of all entries. Operator counts do not establish independence. A two-of-three mirror quorum must not be described as Byzantine fork prevention for one fault. Source revisions and deviations are recorded in the [adapter catalog](adapters.md), rather than attributed wholesale to IETF MTC.

## Dependency order and cycles

The current operation commits in this order:

```text
external trust and policy -> qualified key and original credential
document scope -> intent -> exact container signing input
-> activation context -> authorization proof -> permit
-> durable dispatch -> document signature -> execution receipt
-> immutable operation evidence -> timestamp -> verification plan
```

CMS control signatures do not require a document permit for signing themselves. Bootstrap trust never comes from the package being evaluated. The container commits to intent/policy and the original credential, not to its own final evidence package. A timestamp covers an already frozen operation layer and excludes itself, refreshed status and the final plan. A renewed timestamp may cover earlier time evidence; it cannot include its own final bytes. [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html) supplies the timestamp token, and [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html) supplies evidence-record renewal structures. The selected input coverage is a separate composition rule.

For batches, the committed ordered contexts omit `batchHash`; the final contexts add that hash. For organizational seals, intent names the authorization ID before the grant signs the activation hash; the later permit commits to that grant. These constructions avoid a reverse dependency on their own resulting signatures. Hash validity alone is insufficient: plan/type checks, authority and all cross-object bindings remain required. No selected construction above requires a hash fixed point; this is a dependency analysis, not a formal protocol proof.

## Durable states, failures and replay

| Boundary | Necessary durable behavior | Failure/recovery limit |
| --- | --- | --- |
| Enrollment | Bind request ID to approved request and issued result | Identical requests return the saved result within the authorized API window; changed input fails. KEM challenge consumption followed by RA denial requires a new challenge, not reuse of the old proof. |
| Signing dispatch | Reserve exact request before contacting the provider; record immutable completion | A crash/lost response remains UNKNOWN_EXECUTION. A stored original result may be returned; retrying `execute()` is not permission to sign again. Request expiry or later revocation may deny that API call, so result lookup is separate. |
| Optional EBP/PSCP recovery | Verify original result against frozen request, admitted key and current applicable policy | Reconciliation never invokes signing. Expiry, revocation or changed binding can prevent reconciliation and leave the operation unknown. EBP keeps its key lock; an administrator cannot simply clear it and claim non-execution. |
| Wrapper rotation | PREPARED -> COMMITTED -> OLD_RETIRED | Root comparison and commit are atomic. Failed commit retains PREPARED; restart after success reads COMMITTED. Old intermediate records require fresh verification after explicit migration. Retirement cannot erase copied wrappers. |
| Trust metadata | Atomic serial/digest watermark with fixed external root pins | Stale/forked LIVE input fails; historical reads do not mutate the watermark. Root rotation, emergency replacement and rollback-resistant operational backups remain separate unimplemented lifecycle obligations. |
| Recovery model | Fixed-point reachability with explicit protected targets | Cycles terminate over the finite node set. An unknown target is an error, not evidence of separation; omitted real-world capabilities remain a deployment risk. |

The local journal's transaction support cannot make a remote signer exactly once. Existing issuance and signing state machines retain this distinction. Reducing their states is justified only when it removes no external side effect, proof obligation or recovery distinction; the wrapper's former intermediate verification state met that condition.

## A second implementation and production verification

An independent verifier can start with ordinary WebAuthn activation, one credential representation, existing CMS or COSE parsing, independently provisioned authority and a complete document evidence plan. It need not implement raw signing, ARKG, PRF vaults or EBP. The same shared subject/key/purpose rules apply to other application tracks.

The current complete baseline is still not independently implemented. Duplicate fields, generic package graphs, custom certificate-status controls, native credential seals and the breadth of candidate profiles make implementation harder. Standards-based container evidence and status should be compared before defining a successor package; interoperability of OpenSSL with CMS alone does not resolve these application-level choices.

The [production parser contract](../spec/bindings/SEP-draft-02.md#2-parser-and-execution-boundaries) requires mature evaluated parsing/crypto stacks plus CertConcord semantic checks. The reference implementation and SDK demonstrate these semantics; neither is the recommended production security boundary. A mature parser does not supply identity qualification, signing authorization, trustworthy time or closure policy on its own.

One concrete parser counterexample is value-equivalent ASN.1 type substitution: an OBJECT IDENTIFIER replaced by a RELATIVE-OID can decode to the same dotted text, and a tagged byte value can match an expected digest without being an OCTET STRING. CMS now rejects both at their schema positions, including signed attributes with a cryptographically valid test signature. The [schema regressions](../reference/security-engineering.test.mjs) exercise these cases. Correct value comparison alone is insufficient; this correction does not establish complete parser correctness.

Adversarial traces are executable in [state security](../reference/state-security.test.mjs), [lifecycle](../reference/lifecycle.test.mjs), [execution recovery](../reference/execution-binding.test.mjs), [SDK results](../reference/sdk-results.test.mjs) and [document evidence](../reference/document-evidence.test.mjs). They cover the named paths and synthetic failure conditions. [Conformance](../spec/conformance.md) continues to distinguish these local results from independent interoperability and security assessment.

The [PassSign transcript clarification](../spec/external/passsign-evidence/draft.md) develops the acyclic timestamp-coverage issue as a separate proposed upstream amendment. It does not replace the current framework evidence encoding or establish PassSign conformance.
