# Selected CAdES preservation profile

This adapter implements a bounded standard CMS preservation path using the published [ETSI EN 319 122-1 V1.3.1](https://www.etsi.org/deliver/etsi_en/319100_319199/31912201/01.03.01_60/en_31912201v010301p.pdf). Its requested levels are CAdES-B-B, B-T, B-LT and B-LTA, represented in the API as `B`, `T`, `LT` and `LTA`. A level is a validation result under the caller's external policy. An attribute's presence alone does not establish a level.

The selected profile uses one SignerInfo identified by issuer and serial number, DER CMS SignedData, `id-data`, attached or explicitly supplied detached content, and P-256/SHA-256 document signatures. Certificates, direct CRLs and RFC 3161 timestamp signatures use the same selected signature suite. Timestamp imprints may use SHA-256 or SHA-512. Trust paths contain one leaf and one explicitly trusted self-signed root. This is a finite-horizon classical profile, without a post-quantum preservation claim.

For the signed SigningCertificateV2 certificate identity, the first ESSCertIDv2 may use the omitted SHA-256 default or an explicit SHA-384 or SHA-512 hash identifier. The verifier hashes the complete DER signer certificate and requires the caller's deadline for the selected identity hash. SHA-384 admission is limited to this certificate binding; it does not select a SHA-384 SignerInfo digest, P-384 signature suite, timestamp imprint or archive hash. A wrong signed certificate hash is invalid even when the CMS signature itself verifies.

The existing [draft-03 CMS and ECP composition](../spec/bindings/DOCUMENT-draft-03.md) keeps its original verifier and exact byte interpretation. The new adapter accepts bare CMS, creates no CertConcord archive wrapper and defines no new cryptographic domain. It does not establish identity qualification, consent, an organizational grant or the original ECP's authorization verdict.

Import these APIs directly from `reference/cades.mjs`. The packaged `createVerifier` SDK exposes the CMS/MDOC ECP plans; the bare-CMS adapter has its own policy and result contract.

## Creation and augmentation

`prepareCAdESSignature` takes `content`, the signer `certificate`, additional `certificates`, `signingTime`, optional `detached`, and the selected `algorithmProfile`. Its `tbs` is the CMS signed-attribute SET input. `finish(signature)` verifies the supplied signature before returning CMS. The required signed attributes are created before signing: content type, content digest, signing time and SigningCertificateV2. The certificate binding hashes the complete certificate, so another certificate containing the same public key cannot replace it.

The minimal API does not infer a media type from opaque content. A caller should supply a known media type using the recommended standard MIME attribute through `additionalSignedAttributes`, or explicitly select the opaque-content exception. Omitting that recommendation alone is not an invalid signature. If CMS algorithm protection is supplied, its digest and signature algorithm must match the actual SignerInfo; a MAC choice is not accepted in this signature profile.

The registered CMS algorithm-protection OID is `1.2.840.113549.1.9.16.2.52` in the [IANA S/MIME attributes registry](https://www.iana.org/assignments/smi-numbers#security-smime-2). RFC 6211 printed `1.2.840.113549.1.9.52`; [draft-ietf-lamps-rfc6211-update-04](https://datatracker.ietf.org/doc/html/draft-ietf-lamps-rfc6211-update-04) describes the correction and remains an Internet-Draft. The verifier also retains the old OID as a distinct compatibility attribute with the same strict encoding and binding checks. If both signed attributes occur, each must independently match the SignerInfo; neither takes precedence. Neither OID is permitted in unsigned attributes. Verification and augmentation do not rename attributes or rewrite their signed bytes.

These checks also apply to the shared CMS mathematical inspection used by S/MIME and RFC 3161 preservation. They do not expand the timestamp service's separate attribute allowlist. In the selected PAdES approval profile, both OIDs are forbidden and produce `INVALID`; a PDF document timestamp is inspected through the RFC 3161 route. The [OID regression tests](../reference/cms-algorithm-protection.test.mjs) cover the registered and legacy attributes, their coexistence and their placement.

The [retained algorithm-protection vectors](../reference/vectors/cms-algorithm-protection.json) preserve 36 signed CMS examples across both OIDs and all four shared inspection profiles. Their [replay tests](../reference/cms-algorithm-protection-replay.test.mjs) bind the exact signed attributes, signer certificate and signature, then compare the complete inspection failure list. These vectors carry no certificate-path, authority, timestamp-service or complete document-preservation verdict.

Self-claimed signing time is not trusted proof of existence. Missing required signed fields cannot be repaired by adding unsigned attributes. All certificates actually used to validate the signer, including the selected root, must be embedded already at B. An embedded root remains data; external trust policy selects the anchor.

`prepareCAdESAugmentation(cms, options)` takes the target level, detached content when needed, `validationMaterial: {certificates, crls}`, the external `policy` and timestamp request options. For T and LTA it returns the exact `requestDER`, `imprint` and `hashOID`. The caller obtains the timestamp externally, then calls `finish(token, {validationTime, knowledgeTime, policy?})`. LT needs no new timestamp. Finish revalidates with explicit current times and can consume an updated complete policy after the external operation. Preparation snapshots the input bytes; later mutation cannot change the signed or timestamped object.

The adapter performs no network request, durable publication or scheduling. A service must retain the exact request and uncertain response state when composing this API with durable storage. Reissuing an uncertain request does not prove that the earlier operation failed.

## Level dependencies

| Level | Required validated dependencies                                                                                                                                      |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B     | Exact content digest and document signature, mandatory signed attributes, signer certificate binding, embedded certificate path and external authority/status policy |
| T     | B plus a trusted signature timestamp over the raw signature value, with a conservative existence bound before signer expiry or applicable revocation                 |
| LT    | T plus the required signer and timestamp certificate/status material in standard SignedData fields                                                                   |
| LTA   | LT plus archive-time-stamp-v3, its verified ATSHashIndexV3 and continuous protection through the evaluation time                                                     |

LT material must close the dependencies of both the document signer and the timestamp signers. Only collecting the document signer's chain is insufficient. Current external material may authenticate the newest timestamp but does not count as embedded LT material or as something protected by an older archive timestamp.

## Archive byte contract

The selected route uses archive-time-stamp-v3 (`0.4.0.1733.2.4`) and ATSHashIndexV3 (`0.4.0.19122.1.5`). Each archive attribute has one token value. Renewals use separate attributes with the same archive OID. The index belongs to the timestamp token's SignerInfo unsigned attributes.

Each index contains the selected hash identifier and hashes of complete certificate choices, complete revocation choices, and each preexisting unsigned attribute value paired with its attribute-type OID. The new timestamp itself is excluded. Prior timestamps are included. Index order follows the source collections for generation; verification resolves exact referenced objects rather than inferring chronology from DER SET order.

The archive imprint hashes, in sequence: the encoded content-type OID; the content hash under the archive hash; the original SignerInfo version, signer identifier, digest algorithm, stored signed-attributes field, signature algorithm and signature field; and the encoded index. The stored signed-attributes field retains its context-specific tag here. The document signature's input uses the CMS SET tag instead. A SHA-512 renewal recomputes the content hash under SHA-512 even when the original document digest was SHA-256.

Removal or replacement of indexed bytes invalidates that proof. Later additions do not invalidate an older index or retroactively become protected by it. This selected profile requires protection of the current material set to report LTA; otherwise the missing augmentation proof is indeterminate at LTA while any established lower level remains distinguishable. Every renewal must preserve the original signed core and all earlier protected objects. Verification checks every layer, including original index resolution and the exact standard imprint.

## Authority, status and time

An authenticated TSU revocation with no reason code is different from an explicit reason `0`. Under [RFC 3161 section 4](https://www.rfc-editor.org/rfc/rfc3161.html#section-4), this profile retains the pre-revocation treatment only for explicit reasons `0`, `3`, `4` and `5`. Other reasons, including key compromise, require an independent proof covering the exact old token before the effective revocation cutoff. Without it, an earlier self-claimed timestamp time yields `INDETERMINATE/CADES_TSA_REVOKED_NO_POE`. Past recovery follows the selected EN 319 102-1 proof rules; material coverage alone is insufficient. A timestamp used at or after authenticated effective revocation remains `INVALID`. An unproven late CRL cannot establish a revocation fact. The public APIs derive token proof times from verified archive coverage, never from a caller-supplied historical proof date.

The caller supplies `validationTime`, the actual `knowledgeTime` and this external policy:

| Field                | Meaning                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| `trustedRoots`       | Exact DER anchors admitted outside the container                                                  |
| `scope`              | External trust domain, issuer identity, `X509` representation and optional profile                |
| `authorityResolver`  | Shared synchronous role resolver, including applicable later-known incidents                      |
| `timestampPolicies`  | Accepted RFC 3161 policy OIDs                                                                     |
| `algorithmDeadlines` | Finite exclusive protection cutoffs by signature algorithm OID                                    |
| `hashDeadlines`      | Finite exclusive protection cutoffs by hash OID                                                   |
| `keyDeadlines`       | Finite exclusive cutoffs keyed by `core.keyID(publicKey)` in hexadecimal                          |
| `currentMaterial`    | Optional external DER certificates and CRLs for current authentication and later-known revocation |

The root is resolved as ISSUER, the CRL signer as STATUS_AUTHORITY at CRL publication time, and a timestamp signer as TIMESTAMP_AUTHORITY at its time interval. No role is inferred merely from possession of a certificate. The same knowledge time reaches these decisions, including when an earlier artifact state is being evaluated.

`validationTime` can select a historical signature evaluation time; `knowledgeTime` records the actual evidence and incident knowledge used now. A signature timestamp must establish existence by `validationTime`. A later archive proof may arrive after that historical time, provided it is known by `knowledgeTime` and protects the earlier layer before its cutoff. The reported level describes the evidence validated with current knowledge; it does not claim that every augmentation already existed at the historical evaluation time.

The selected CRL profile is v2, full, direct and root-signed, with a matching authority key identifier, root subject key identifier, CRL number and nextUpdate. Delta, indirect and partitioned CRLs are outside this profile. A CRL issued after the target certificate expired cannot prove an absent serial was still good: the initial implementation does not implement expired-certificate retention declarations. Authenticated applicable revocations remain relevant even when that CRL cannot supply positive freshness evidence.

[RFC 5280 section 4.1.2.2](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.2) requires a CA to assign positive, issuer-unique certificate serial numbers and separately advises certificate users to handle nonconforming zero or negative serials gracefully. For this selected direct-root CAdES profile, a signed external certificate with serial zero can be inspected and parsed, but complete material validation returns `UNSUPPORTED/CADES_CERTIFICATE_SERIAL_UNSUPPORTED`. The selected complete-CRL parser admits only positive revoked-certificate serials, so it cannot establish the required zero-serial status binding. The outcome does not turn an otherwise valid CMS signature into a trust decision. A positive-serial control remains admissible, while a zero-serial CRL entry returns `INVALID/CADES_CRL_ENTRY`. The shared material helper carries this boundary into adapters that call it; negative-serial reception is not expanded here. [Signed positive and zero controls](../reference/certificate-serial-boundary.test.mjs) and their [case contract](../reference/vectors/certificate-serial-boundary.json) exercise the selected result.

Under [RFC 5280 section 5.1.2.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.1.2.6), `revokedCertificates` is absent when no certificates are revoked; an explicitly present empty SEQUENCE is rejected. A present `crlEntryExtensions` has at least one Extension under the RFC 5280 `Extensions ::= SEQUENCE SIZE (1..MAX) OF Extension` definition; an absent extension field is allowed. [Frozen signed CRL admission vectors](../reference/vectors/cades-crl-admission.json) cover the absent, empty and nonempty forms through the complete CAdES verifier.

For a document signer certificate, this selected profile rejects a present empty cRLDistributionPoints, authorityInfoAccess or subjectInfoAccess SEQUENCE, and a present empty issuerAltName GeneralNames SEQUENCE. Each present cRLDistributionPoints member must contain a distributionPoint or cRLIssuer; a member encoded as an empty SEQUENCE is rejected. These are bounded certificate admission rules based on [RFC 5280 section 4.2.1.13](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.13) , [section 4.2.1.7](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.7), [section 4.2.2.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.1) and [section 4.2.2.2](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.2). For the document signer leaf, this profile rejects a subjectAltName GeneralName with empty content, including an empty dNSName, and a directoryName wrapping an empty Name. These additional admission checks apply to the CAdES document signer leaf. [RFC 5280 section 4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.6) prohibits conforming issuers from using empty GeneralName fields but leaves client path behavior undefined; this rejection is CertConcord's explicit selected-profile decision. Absent extensions and the signed nonempty controls remain admissible. [Frozen signer certificate and ESS-bound CMS vectors](../reference/vectors/cades-certificate-extension-cardinality.json) and their [complete-verifier replay](../reference/cades-certificate-extension-cardinality.test.mjs) cover these boundaries.

For the selected CAdES document signer leaf, a present subjectAltName otherName must carry a DER OBJECT IDENTIFIER type-id followed by one [0] EXPLICIT value. An ediPartyName must carry [1] partyName, optionally preceded by [0] nameAssigner. An iPAddress has exactly four IPv4 or sixteen IPv6 octets, and a registeredID contains a minimally encoded DER OBJECT IDENTIFIER. These [RFC 5280 section 4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.6) GeneralName forms and [ITU-T X.690 section 8.19.2](https://www.itu.int/rec/T-REC-X.690-202102-I) OID encoding rules are selected certificate admission boundaries; malformed forms return `INVALID/CADES_CERTIFICATE_SAN`. RFC 5280 leaves client behavior for malformed noncritical SAN unspecified, so this is an explicit CertConcord profile decision. The [frozen signed signer certificate and CMS vectors](../reference/vectors/cades-signer-san-generalname.json) and [complete-verifier replay](../reference/cades-signer-san-generalname.test.mjs) cover the selected forms, including valid optional nameAssigner and IPv6 controls; they do not establish all GeneralName semantics or name-constraint processing.

For the selected CAdES document signer leaf, subjectAltName, cRLDistributionPoints and freshestCRL fullName, and authorityInfoAccess and subjectInfoAccess accessLocation admit only the defined GeneralName CHOICE tags [0] through [8]. A subjectAltName ediPartyName mandatory [1] partyName and optional [0] nameAssigner each wrap one DirectoryString choice: UTF8String, PrintableString, TeletexString, UniversalString or BMPString. [RFC 5280 section 4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.6) defines GeneralName and EDIPartyName, while [section 4.1.2.4](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.4) defines DirectoryString. [Sections 4.2.1.13](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.13) and [4.2.1.15](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.15) define CRLDP and the same-syntax freshestCRL points; [sections 4.2.2.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.1) and [4.2.2.2](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.2.2) define AIA and SIA accessLocation. The selected profile returns the extension-specific `CADES_CERTIFICATE_SAN`, `CADES_CERTIFICATE_CRLDP`, `CADES_CERTIFICATE_FRESHESTCRL`, `CADES_CERTIFICATE_AIA` or `CADES_CERTIFICATE_SIA` reason for the tested malformed form. The [frozen signed certificate and ESS-bound CMS pairs](../reference/vectors/cades-signer-generalname-structure.json) and [complete-verifier replay](../reference/cades-signer-generalname-structure.test.mjs) cover six one-tag structural mutations and their valid controls. A present freshestCRL must also contain at least one DistributionPoint under the RFC 5280 section 4.2.1.15 reference to the section 4.2.1.13 `SEQUENCE SIZE (1..MAX)` syntax. The [signed one-point and empty-point controls](../reference/vectors/cades-signer-freshestcrl-cardinality.json) and [complete-verifier replay](../reference/cades-signer-freshestcrl-cardinality.test.mjs) exercise this separate cardinality boundary. This is an explicit signer admission choice, not a universal receiver rule or an exhaustive implementation of GeneralName contents, AIA/SIA methods, name constraints or URI retrieval.

For the selected CAdES document signer leaf, a present subjectAltName `uniformResourceIdentifier` or `dNSName` uses IA5 octets below `0x80`; a `dNSName` or the DNS-form domain of an `rfc822Name` cannot contain an empty interior label. [RFC 5280 section 4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.6) defines these IA5String GeneralName forms, requires the dNSName preferred syntax of [RFC 1034 section 3.5](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.5) as modified by [RFC 1123 section 2.1](https://www.rfc-editor.org/rfc/rfc1123.html#section-2.1), and references the [RFC 2821 section 4.1.2](https://www.rfc-editor.org/rfc/rfc2821.html#section-4.1.2) Mailbox grammar for rfc822Name. A malformed selected signer SAN returns `INVALID/CADES_CERTIFICATE_SAN`. This is an explicit signer admission decision; the cited issuer syntax does not impose a universal relying-party rejection rule. The [frozen signed certificate and ESS-bound CMS pairs](../reference/vectors/cades-signer-san-lexical.json) and [complete-verifier replay](../reference/cades-signer-san-lexical.test.mjs) cover these four octet-level cases. They do not establish full URI parsing, DNS or mail authorization, address-literal semantics, name constraints, PAdES or production trust.

For that selected signer leaf's `dNSName`, each nonempty label has at most 63 ASCII octets and begins with an ASCII letter or digit; a leading hyphen is rejected. These two admission boundaries follow the preferred syntax in [RFC 1034 section 3.5](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.5), with the first-character digit allowance in [RFC 1123 section 2.1](https://www.rfc-editor.org/rfc/rfc1123.html#section-2.1), as incorporated by [RFC 5280 section 4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.6). A violating signer certificate returns `INVALID/CADES_CERTIFICATE_SAN`. The [signed 63/64-octet and first-byte controls](../reference/vectors/cades-signer-san-dns-lexical.json) and [complete-verifier replay](../reference/cades-signer-san-dns-lexical.test.mjs) cover these two bounded decisions. They do not establish exhaustive preferred-name syntax, DNS authorization, universal receiver behavior, PAdES or production trust.

For the selected CAdES document signer leaf, each present cRLDistributionPoints member contains only the ordered `distributionPoint` [0], `reasons` [1], and `cRLIssuer` [2] fields, with no duplicate or unknown fields. A fullName URI must be nonempty IA5 text. An implicitly tagged ReasonFlags BIT STRING must encode 0 through 7 unused bits and zero unused trailing bits. When a cRLIssuer directoryName is byte-identical to this certificate's issuer Name, this selected CA issuance profile requires the direct-issuer form to omit cRLIssuer; a distinct indirect issuer is not rejected solely because [2] is present. These are scoped certificate admission rules under [RFC 5280 section 4.2.1.13](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.13) and [ITU-T X.690 sections 8.6.2.2 and 11.2](https://www.itu.int/rec/T-REC-X.690-202102-I); the direct-issuer omission is a rule for conforming CAs adopted by this selected profile, not a universal receiver rejection requirement. The [frozen signed certificate and CMS controls](../reference/vectors/cades-signer-crldp.json) and [complete-verifier replay](../reference/cades-signer-crldp.test.mjs) cover four malformed forms plus nonempty URI, valid ReasonFlags and relative-name controls. They do not establish full URI semantics, indirect CRL validation or CRL retrieval.

For the document signer leaf, a present noncritical certificatePolicies extension must contain at least one PolicyInformation with a policy OID. Its optional policyQualifiers field, when present, must contain at least one two-field PolicyQualifierInfo; the same policy OID must not appear twice in the extension. These are structural admission rules from [RFC 5280 section 4.2.1.4](https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.4). An absent extension, a single policy without qualifiers, distinct policies, and a structurally nonempty CPS URI qualifier remain admissible in the frozen signed controls. This selected CAdES route still rejects a critical certificatePolicies extension and does not evaluate policy-path applicability or dereference a CPS URI. The [frozen signer certificate and ESS-bound CMS policy vectors](../reference/vectors/cades-certificate-policies.json) and [complete-verifier replay](../reference/cades-certificate-policies.test.mjs) cover these limits.

For an `id-ecPublicKey` end-entity document signer with `keyUsage`, the selected [RFC 5480 section 3](https://www.rfc-editor.org/rfc/rfc5480.html#section-3) profile admits `digitalSignature`, `nonRepudiation` (also called `contentCommitment`) and `keyAgreement`. An `encipherOnly` or `decipherOnly` bit requires `keyAgreement`; this selected profile also rejects both direction bits together and rejects `keyEncipherment` or `dataEncipherment`. The [RFC 5280 keyUsage meanings](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.2.1.3) do not turn an EC signing certificate into a key-transport or key-agreement proof. This check applies to the CAdES document signer, not the TSA or S/MIME recipient profile. The [frozen signed EC signer vectors](../reference/vectors/cades-ec-signer-key-usage.json) and [complete-verifier replay](../reference/cades-ec-signer-key-usage.test.mjs) include valid and rejected combinations; they do not exercise a key-agreement operation.

Release from certificate hold is an unselected transition in this profile. A non-TSA target with an authenticated earlier `certificateHold` entry and an otherwise admissible, selected positive complete CRL omitting that serial returns `UNSUPPORTED/CADES_CRL_HOLD_RELEASE_UNSUPPORTED` when the selected CRL has a strictly greater number and later thisUpdate, not before the recorded revocationTime and at or before the evaluated state time. Its thisUpdate proves a snapshot, not the release instant. Both CRLs must satisfy the existing root, authority and authenticity requirements; any known CRL-number conflict prevents this classification. A missing, stale, later-than-state, unknown, post-expiry or unauthenticated clearing snapshot cannot replace the existing hold result. Permanent revocations, later applicable holds and other established invalid findings retain precedence. The TSA reason and independent signature-proof rules are unchanged. This boundary also applies through the shared PAdES and current-use S/MIME material helpers; it never makes admission valid. [RFC 5280 section 5.2.4](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.2.4) recognizes release from hold; its delta-CRL mechanism does not itself define archival hold intervals for this selected complete-CRL profile.

[Raw full-CRL hold transition vectors](../reference/vectors/cades-hold-release.json) cover the public CAdES B result boundary, including permanent, historical, conflicting, stale and invalid-signature controls.

Historical freshness requires a later authenticated archive proof over the exact certificates and CRLs used for that decision. A self-claimed publication date or signing time cannot supply that proof. `knownCRLs` gives the material helper all later-known container CRLs for revocation evaluation; it does not enlarge the historical positive material set. An archive timestamp cannot establish the authenticity of its own otherwise unprotected validation inputs. The newest archive layer needs currently admissible external authority and fresh status evidence.

These authenticity rules also apply to negative CRL entries. Exact historical CRL bytes need proof before the root key/signature/hash cutoff; other CRLs need current cryptographic acceptability at knowledge time. A claimed old thisUpdate value does not authenticate a newly found CRL after that cutoff. Such unproven revocation knowledge is indeterminate, not an established certificate revocation.

Timestamp accuracy must be present. Absent accuracy is indeterminate in this profile, and is never interpreted as zero. The full conservative interval must fit the applicable certificate and authority conditions. The initial signature proof and every later archive proof must arrive before the relevant protection cutoff; equality fails. The final unprotected layer must remain cryptographically admissible at `knowledgeTime`, including a bare B signature when no trusted timestamp exists. Choosing an earlier `validationTime` cannot authenticate a token after its key, signature or hash protection is lost. A newly created token cannot repair an interval already lost to a cutoff.

Timestamp generation times have at most millisecond fractional precision in this implementation. A present TSA GeneralName must be a directoryName matching the actual timestamp certificate subject; other name forms are unsupported. Signature signingTime uses the CMS-required UTCTime form for years 1950 through 2049.

Ordinary certificate expiry limits new certificate use; it is not by itself the protection deadline of an already preserved signature. Conversely, a later-known key compromise cannot be defeated by presenting a token with a conveniently old claimed generation time. Key cutoffs are authenticated external policy at the actual knowledge time and constrain when a successor proof had to be obtained.

Without trusted signature proof of existence, a certificate or root that is outside its validity interval at evaluation leaves the claimed signing time unresolved, so the result is indeterminate. This does not hide an invalid signature, an authenticated applicable revocation or a lost key-protection interval.

## Results and unsupported input

`verifyCAdES` takes `minimumLevel` and returns an overall typed result, reason and requested/verified level information. Established malformed encoding, bad bindings, invalid signatures, indexed-byte changes and applicable revocation are INVALID. Recognized unselected capabilities are UNSUPPORTED. Missing mandatory evidence, insufficient knowledge, missing policy, absent timestamp accuracy and stale status are INDETERMINATE. INVALID takes precedence over UNSUPPORTED, which takes precedence over INDETERMINATE; every non-VALID result prevents acceptance.

The initial profile does not implement multiple document signers, subject-key-identifier SignerInfo selection, BER, intermediate or delegated paths, OCSP, additional signature suites, legacy certificate/revocation value and reference attributes, countersignatures or certified-attribute assertions. Its DER parser rejects noncanonical and indefinite-length encodings as malformed; it does not independently determine whether rejected input would be valid under BER. These boundaries must not trigger a retry with weaker rules. The optional `originalCMS` input checks exact signed-core and effective-content continuity with an original CMS object, including retention of every original unsigned attribute value; its acceptance does not import any separate authorization result.

The [detached preservation path](document-preservation.md) archives the complete original ECP and CMS bytes. Adding unsigned CMS data changes that original leaf's whole-object hash. Preserve and verify the original ECP separately; replacing its CMS leaf with augmented CMS while reusing the old document timestamp is invalid.

## Standards and assurance boundaries

The source selection uses EN 319 122-1 V1.3.1 for CAdES and [EN 319 102-1 V1.4.1](https://www.etsi.org/deliver/etsi_en/319100_319199/31910201/01.04.01_60/en_31910201v010401p.pdf) for the reviewed validation process. The direct-root helper does not implement the latter's complete path building, constraint set or validation-report schema. [TS 119 312 V2.1.1](https://www.etsi.org/deliver/etsi_ts/119300_119399/119312/02.01.01_60/ts_119312v020101p.pdf) informs suite selection; this P-256-only verifier does not claim support for all algorithms in its tables. SHA-512 imprints do not make classical timestamp signatures post-quantum safe. Deadline values are external assessments, not invented ETSI migration dates.

[TS 119 122-3 V1.2.1](https://www.etsi.org/deliver/etsi_ts/119100_119199/11912203/01.02.01_60/ts_11912203v010201p.pdf) defines a separate CAdES evidence-record route. That route preserves original ContentInfo encoding and has different mutation rules. Neither standalone ERS nor its internal/external evidence-record attributes substitute for the ATSv3 baseline path implemented here. The selected API reports those attributes as unsupported.

The official published versions were rechecked on 2026-10-07. ETSI work items also showed development versions EN 319 102-1 V1.4.2 and TS 119 312 V2.1.2.
