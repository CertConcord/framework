# Adapter profiles — draft reference

An adapter is selected by its identifier and wire profile. Its binding, validation and failure rules are mandatory when enabled. Inputs outside its declared profile MUST be rejected. Exact upstream bytes are identified by [source-lock.json](../reference/source-lock.json).

This catalog supplies concrete bindings for the `certconcord-governed-draft-03` composition. [FRAMEWORK draft 03](../spec/bindings/FRAMEWORK-draft-03.md) defines architectural succession and wallet ecosystem independence. A source lock fixes one evaluated selection; it does not prevent adopting later drafts, final standards, independent holder architectures or original designs. New selections document compatibility findings, authenticated selection, evidence rules and cutover. They need not be backward compatible. A successor to MTC may revise the architecture and adapter interfaces instead of fitting the old contract. EUDI mappings remain optional. A registry entry alone does not implement or authorize a new binding.

## Boundaries and compatibility rules

### MTC and transparency

The MTC cryptographic certificate profile remains draft-06, including its Appendix C tree vectors. The selected C2SP transport revision is independently locked. Transport availability does not imply MTC draft-07 compatibility.

The [upstream baseline](upstream-baseline.md) identifies the reviewed publication and editor revisions. C2SP cosignatures select the current editor text at the common pinned snapshot; its presentation-language reference and structure-name changes preserve the selected signature bytes. An editor snapshot is not a final C2SP release.

MTC plus C2SP mirror/witness protocols plus RRA governance is CertConcord's composition. The upstream formats, selected operator/quorum policy and CertConcord document requirements have separate provenance and assurance claims. A witness's consistency statement does not acquire a mirror's durable-entry-possession meaning from the transport used to carry it.

Draft-06 section 6.4.3 includes a predecessor in a sequence of active landmarks, but its printed upper-bound test excludes the first sequence's two entries when the latest number is one. `certconcord-mtc-landmarks-v1` uses the explicit `count <= latestNumber + 1` bound while retaining the predecessor and all interval checks. `parseLandmarks(..., {draft06Strict:true})` enforces the printed draft bound instead. [Upstream PR 337](https://github.com/ietf-plants-wg/merkle-tree-certs/pull/337) already corrected the bound in the current editor text, pinned as `mtcEditor`. The implementation agrees with that correction; it is not a new upstream proposal. The named draft-06 compatibility boundary remains explicit, and this one correction does not establish support for the editor's other changes.

C2SP's pinned ML-DSA-44 cosignature encoding retains its standard key identifier. ML-DSA-87 uses the distinct `CERTCONCORD-MLDSA87-SUBTREE-v1` identifier and domain. A peer must explicitly enable it. It is not advertised as C2SP's ML-DSA-44 profile.

The reference issuer bounds a log to 4,096 entries and 12 MiB. Mirrors enforce configured entry and byte limits. Capacity exhaustion requires an authorized new log under the lifecycle policy. In-memory whole-log hashing is intended for bounded logs; changing storage to a persistent tile service must preserve exact leaf bytes and proofs.

### Credential and native platforms

OpenID4VCI, OpenID4VP and HAIP adapters select their 1.0 Final editions. The separately pinned 1.1 editor drafts and their JOSE HPKE/Interactive Authorization dependencies are research comparisons in the [upstream baseline](upstream-baseline.md). The current ECDH-ES JWE and authorization flows do not advertise those new capabilities; ISO Annex C HPKE does not imply JOSE HPKE support.

`PersonalMdocCA` connects signing-credential issuance to a scoped RAR and active device/document-key binding. `RRACredentialIssuer` supplies the auxiliary qualification profile. The generic OpenID engine is suitable for explicit host compositions and protocol tests; it does not supply identity policy. `OpenIDWallet` supports either a local test key or an asynchronous native `holderSigner` returning ES256 P1363 bytes. `holderSigner(provider, keyRef)` in `native-driver.mjs` converts the provider signature format and verifies it against the pinned public key.

The Swift/Kotlin key-provider applications expose generation, public-key retrieval and signing. Wallet composition connects these operations to OpenIDWallet through an authenticated application bridge, with registered app identity, origin/associated-domain policy and any required OS wallet entitlements. Apple managed-key access uses the exact enrollment-certificate fingerprint and app-authorized SecIdentity; an inaccessible identity produces an error. Android signs only after the per-operation BiometricPrompt succeeds. The Windows provider checks the stored SPKI pin and supports Certify through an enrolled AK.

X.509 validation selects a bounded profile: explicit trust anchors, validity, signatures, CA/key-usage/path-length constraints, role-specific mdoc EKU and rejection of unsupported critical extensions. Name constraints and policy-mapping ecosystems require their own validated path engine; the adapter rejects their critical extensions. Online credential status is independent of CA certificate revocation. Deployed registries must provide current CA/DS/reader revocation decisions before admitting their certificates.

The RRA signing/qualification namespaces and status claims are ecosystem-defined. Identity intake applies its selected mDL, photo ID, PID or custom rulebook and status policy. A government or other accepted issuer may issue the RRA signer profile directly, as a standalone or combined mdoc. The signing namespace does not redefine the identity namespaces or create a standard MSO revocation extension. ISO wire behavior is pinned to the published edition and cross-checked with the locked OpenWallet Foundation Multipaz sources.

`identity-profiles.mjs` implements typed admission schemas, including requests spanning multiple namespaces. `ISO_MDOC` and `EUDI_PID_ARF_1_4` select distinct Document Signer and Reader EKUs through trusted configuration. PID values follow the named ARF revision, including its registration dependency. A different ecosystem certificate profile requires an explicit validation adapter; a type alias cannot change certificate trust. The [EUDI architecture mapping](eudi-architecture.md) supplies the corresponding component/lifecycle requirements without defining a separate wallet-attestation wire adapter.

### Providers and document containers

PSCP connects both selected raw-signing extension revisions to the normal RA, certificate and native mdoc paths. The parent authentication key never becomes the document key. Its signature authenticates the returned raw signature, while the independently certified signing key signs the exact document-container input. `PREAUTHORIZED_EVIDENCE` requires an earlier activation permit and explicit dual-proof verification. It does not assert an exclusive hardware permit parser. The selected certificate container is CMS; the selected native mdoc container is COSE with mandatory raw evidence.

`raw-signing.mjs` consumes server-configured attestation roots, current certificate status and approved model policy. Model approval binds the exact AAGUID, custody, non-exportability, algorithms and extension revisions. ARKG certifies an individually derived P-256 SPKI after possession verification; the seed COSE structure is never used as a certificate SPKI. The browser driver requires the selected extension and fails on absence or version mismatch. [PSCP](../spec/bindings/PSCP-draft-03.md) defines these mandatory admission and operation rules.

ARKG public derivation uses revision 11's P-256 construction and vectors. Split-signing revision 01 supplies the operation/verification distinction and `COSE_Sign_Args` reference; selected preview identifiers remain specific to the vendor interface. Neither reference enables unimplemented suites or makes raw signing a prerequisite for ordinary WebAuthn activation.

WebKit's proposed `crypto.subtle.getRemoteKey` interface and RRA's HTTPS RemoteCryptoKey service are distinct adapters. The WebKit driver implements the proposed browser call and verifies its output under an admitted public key; a deployment supplies the platform broker and exact-key/permit integration. It neither substitutes the HTTPS adapter for that browser API nor infers custody from a CryptoKey flag.

CSC, Google KMS and native hardware adapters implement the algorithms their APIs expose. The selected ES256 profiles cannot sign an ML-DSA document. A provider capability mismatch rejects the operation. They may provide the holder operation for INDEPENDENT_PQ or the separate document operation under the explicitly authorized DEVICE_KEY profile.

The PDF adapter accepts bounded unencrypted PDFs with classic xref tables and preserved incremental revisions. It rejects object/xref streams, unsupported DocMDP/FieldMDP transforms and content-changing later revisions. CMS/JWS construction plus selected ETSI attributes does not establish every PAdES/CAdES/JAdES Baseline B/T/LT/LTA property. Timestamp and archive adapters supply actual additional evidence; a relying-party policy must validate the corresponding container-specific level.

CMP selects p10cr and explicit confirmation. It does not advertise CRMF request families, password-MAC protection, implicit confirmation or encrypted private-key delivery. ACME selects DNS-01 and a declared certificate profile; DNS control never substitutes for RA identity approval.

ACME account authentication uses ES256 independently of the certificate's algorithm and purpose. Key rollover verifies both signatures against the fixed key-change URL, binds the account URL and old key, and consumes a fresh outer nonce. The replacement key must satisfy the same account algorithm and protected-header profile. A key registered to another account, including a deactivated account, produces a 409 problem response with that account's Location. Registration and rollover serialize key uniqueness checks and account writes in a journal transaction; rollover also checks the authenticated account revision. Contact data, orders and completed authorizations survive rollover, while subsequent requests must use the replacement key.

The client rejects a CSR containing its current account key, and finalization rejects a CSR containing any currently registered account key before invoking RA approval. The adapter does not maintain a historical index of retired account keys; deployments must retain any additional key-reuse history required by their policy. Neither account authentication nor successful DNS validation authorizes a document certificate without the separate RA decision. `acme.test.mjs`, `security-engineering.test.mjs` and `enrollment-network.test.mjs` exercise key conflicts, algorithm constraints, signature and route substitution, nonce reuse, account lifecycle and certificate-key separation.

### Persistence and parsing boundaries

`certconcord-postgres-journal-v1` implements SEP transaction semantics across service processes. `certconcord-indexed-merkle-v1` preserves existing MTC and C2SP proof encodings using immutable indexed rows. Their schema, recovery constraints and explicit migration procedures are defined in [STORAGE.md](storage.md). PDF verification calls the bounded worker interface in `pdf.mjs`; `pdf-structure.mjs` is an internal parser and does not establish cryptographic validity.

### Governed execution binding

`certconcord-execution-binding-draft-03` implements the [Execution Binding Profile](../spec/bindings/EBP-draft-03.md) for admitted message-signing brokers. The implementation freezes original input, verifies signed admission and permit authority, preserves monotonic epochs and durable key locks, and validates distinct CMS/mdoc ECP plans. ML-DSA and P-256 software providers exercise its executable protocol; native/HSM deployment claims additionally require exclusive backend admission. Proposed authenticator and WebKit interfaces in the draft are not registered as implemented adapters.

### Historical verification

The executable ECP plan trusts an explicitly pinned activation authority's attestation, checks every document/SIM/permit/receipt/certificate/status binding, and reports `ATTESTED_VALID`. The plan requires an explicitly trusted activation attestor; direct hardware-consent evidence uses a separately identified verification plan. Trusted time is a separate assertion. Other evidence graphs are accepted only by their declared semantic plan, never solely because their hashes form a closed graph.

Independent component ownership, immutable pins and integration boundaries are recorded in [components](components.md). The ML-DSA-87 experimental key hint and subtree encoding come from the selected cosignature component; standard ML-DSA-44 identifiers retain their C2SP definition.

The selected mirror adapter is `certconcord-c2sp-mirror-v2` / `C2SP-20261007-MLDSA87-v2`.
A subtree request carries exactly one selected witness note signature. A successful
response is the raw ML-DSA-87 signature in padded base64 followed by LF; the old
signed-note response is rejected. A published checkpoint must also contain a
cryptographically valid signature from the admitted log. The unchanged
`CERTCONCORD-MLDSA87-SUBTREE-v1` identifier selects the experimental signature
algorithm and key hint, not the transport revision.
