# CertConcord draft verifier

Package: @certconcord/verifier, version 0.3.0-draft.1. The experimental API exports `createVerifier`, `createOrganizationHistorySource`, `createOrganizationHistoryVerifier` and `profiles`. The generic verifier evaluates the selected CMS/MTC/X.509 or native signer-mdoc/COSE evidence plan, including supported Passkey and execution-binding candidates. The dedicated organization export evaluates retained complete-package evidence and ERS preservation. It is not a stable API or a complete independent conformance assessment.

This package demonstrates protocol semantics and supports interoperability testing. Its bundle includes custom DER, CBOR and CMS parsing from the reference implementation. It is not a recommended production verifier or parser security boundary. Production implementations SHOULD use mature, independently evaluated parser and cryptographic stacks for the enabled formats and algorithms, while enforcing CertConcord's additional semantic checks: exact original bytes, duplicate/critical-field handling, algorithm and key purpose, external trust, operation authorization, lifecycle, time and evidence completeness. See [the parser contract](../../spec/bindings/SEP-draft-03.md#2-parser-and-execution-boundaries). Worker isolation and passing the test suite do not replace that evaluation.

```js
import { createVerifier } from '@certconcord/verifier';
const verifier = createVerifier({ format: 'CMS', trust: relyingPartyTrust });
const result = verifier.verify(evidenceBytes);
if (result.overall === 'VALID') {
  // Apply the application's access and disclosure policy separately.
}
```

The trust argument comes from authenticated relying-party configuration. Every CMS and native mdoc plan requires `raCertificate`, explicit issuer identity/key scope and `authorityResolver`. Issuer/root pins, MTC members and quorum, credential-seal and activation/receipt authorities, expected policy and trust domain must not be supplied by the evidence being checked. The resolver evaluates each required role and scope at stateTime under evidence known by knowledgeTime; a certificate pin alone is not role authorization. PSCP requires the authoritative passkeyStatus callback. A selected execution-binding policy additionally requires executionBindingCertificate and an executionStatus callback. Incorrect verifier configuration throws before input evaluation.

Selecting the [document evidence binding](../../spec/bindings/DOCUMENT-draft-03.md) adds the required timestamp and any independent organizational grant. Organizational seals require an externally configured organization-to-authority mapping. Required trusted time needs a TSA certificate, issuer key, policy OID and a status callback receiving generation time, proof upper bound and knowledge time. That callback must evaluate relying-party-authorized status information; an unconditional callback is appropriate only to an explicitly synthetic fixture.

## Results

The [organization history contract](../../docs/organization-history.md) defines the dedicated `{trust, authorityResolver, readKnowledge, preservationPolicy}` constructor and `verify({originalBytes, evidenceRecord})` method. It returns `historicalAuthorization` at the first exact PoE bound P under P knowledge, `currentAdmissibility` at P under latest K knowledge, and continuous `preservation` through K. All three must succeed. Its original workload claim is authority-attested; it consumes no live operator or execution snapshot and grants no current signing, recovery or output-release permission. Latest knowledge must retain incidents and conflicts. The generic `createVerifier` does not route this plan.

The [declarative source](../../docs/organization-history-source.md) accepts `createOrganizationHistorySource({configuration, readKnowledge})`, then `createOrganizationHistoryVerifier({source})`. Configuration contains public trust material and finite policy bounds; the reader supplies exact signed authority history, status material and K. The shared implementation authenticates those inputs. Neither the reader nor a corpus expectation supplies an authority decision. Memory sources preserve the same complete verification result contract as equivalent callback inputs. Passing `databasePath` selects a dedicated SQLite source that reauthenticates retained raw material across process restarts. Durable results include a `knowledgeReceipt`; only confirmed commits can accompany a VALID durable result. `readEvidence` returns exact candidate bytes labelled `UNVERIFIED_BYTES`, never a saved authorization. Configuration changes require a different database, and complete database rollback is not detectable without an external anchor.

| overall       | Meaning                                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| VALID         | The implemented checks for the selected policy succeeded. This does not independently grant application access or legal status.                 |
| INVALID       | Malformed encoding, inconsistent commitments, failed signatures or a failed applicable policy check.                                            |
| INDETERMINATE | Required evidence/accuracy is unavailable, selected CMS/organizational status is stale or unknown, or required trusted time is not established. |
| UNSUPPORTED   | A structurally valid schema, plan or explicitly classified algorithm/critical-feature boundary is not implemented by this verifier.             |

All non-VALID results prevent acceptance. Every input-evaluation result includes `overall`, a nonempty `reason`, `coreRevision: 'draft-03'`, `profile` and `dimensions`. `profile` is the parsed candidate plan label, or `null` before a usable label is available; it does not imply that the profile was accepted. Verifier-configuration errors still throw before input evaluation.

`dimensions` may contain `integrity`, `issuerTrust`, `qualification`, `keyBinding`, `authorization`, `status`, `time` and `transparency`. Each included entry contains its own `overall` and nonempty `reason`. An omitted dimension has not been established by the completed checks. A VALID dimension covers the selected policy's checks only; a time result based on execution time does not assert a trusted existence proof. An unused trust mechanism does not produce a VALID dimension.

An established invalid commitment, signature or applicable policy check takes precedence over missing or unsupported evidence. For supported flat plans, available independent checks may establish failure even when another required leaf is absent. Missing dependencies are not fabricated, and unknown plans do not select a fallback. Distinct failed dimensions retain their results even when they share a reason code. With no established invalid check, a required unsupported capability takes precedence over missing evidence. Explicit capability classification covers the selected CMS, COSE and native mdoc boundaries; it does not promise support or classification for every external container or future extension. CRL, OCSP, Status List and experimental status evaluators retain their own four-way contracts.

The [public document corpus](../vectors/document-acceptance-mtc07-rar2/README.md) preserves original bytes, external trust inputs, fixed knowledge times and expected results. Run `node reference/verify-vectors.mjs` from the repository root. `npm run sdk:test` repeats the document cases through the installed tarball's public `createVerifier` export. This is reproducible draft acceptance evidence, not a second independently developed verifier.

The separate [organization history corpus](../vectors/organization-history-rar2/README.md) retains original packages, EvidenceRecords, external source configuration and signed knowledge inputs. `node reference/verify-organization-vectors.mjs` compares complete results, including both historical views, preservation, exact times and detailed checks. The installed-package consumer repeats those saved cases through both public organization factories in a separate process with network and private signing disabled. Replay does not import the corpus authoring tools or generate replacement evidence. Additional distinct consumer processes retain a committed compromise through a GOOD-only refresh and require current status after reopening a previously positive database; they compare complete results and recover exact stored originals with clock, network and private signing disabled.

Verification is synchronous and does not fetch evidence URLs. Input is deterministic CBOR, limited to 16 MiB by default and at most 64 MiB by configuration. Use a resource-limited worker for hostile inputs. Deep imports, private-key custody, signing services, enrollment and live operation state are outside the API.

Build with npm run sdk:build from the repository root. Install the generated reference/dist/certconcord-verifier-0.3.0-draft.1.tgz locally. The package is private to prevent registry publication, while tarball installation is supported. The manual draft-artifact workflow produces review artifacts; no stable GitHub release or npm publication is configured. The package contains Apache-2.0 software and bundled dependency notices; original documentation is CC-BY-4.0.

The previous research SDK's VALID_UNDER_POLICY and REJECTED strings are not this draft API's contract. Consumers must explicitly handle all four values above. Draft 03 uses domain-array version 3 and a schema-2 flat evidence package. Older wire domains and nested packages are unsupported; callers must preserve any historical original bytes rather than rewriting them into this revision.
